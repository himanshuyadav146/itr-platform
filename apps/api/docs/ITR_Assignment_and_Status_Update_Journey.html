ITR Assignment & Status Update – Process Documentation

This document describes two core journeys in detail: ITR Assignment and Status Update, including APIs, database tables, data flow, and flowcharts. Use it to decide the next steps for your system.

Part 1: ITR Assignment Process

1.1 Overview

Purpose: An admin (or authorised user) assigns an ITR case (itr_detail.id) to a tax professional (ACCOUNTANT or CA). The assignment is stored so the professional can work on the case and the client can see "Tax Expert Assigned" in the status flow.

Outcome: The ITR is linked to a professional; optionally the status workflow is updated so the "expert_assigned" step appears as completed to the client.

1.4 Step-by-Step Assignment Flow

  1. Admin opens ITR list – Calls GET /admin/itrs.php. Response includes itrDetails[].itrId.
  2. Admin selects an ITR and a professional – e.g. itrId 24, professionalId 2.
  3. Admin calls POST /admin/assign_itr.php – Body: { "itrId": 24, "professionalId": 2 }, Authorization: Bearer <admin token>
  4. assign_itr.php logic – Validates token (ADMIN); validates itrId and professionalId; checks itr_detail for id=24 and gets userId; checks users for professional Role ACCOUNTANT/CA; checks no active assignment; INSERT into itr_assignments; optionally gets order_id from payment_info for client and calls StatusHelper::updateStatusStep(..., 'expert_assigned', true) to write itr_order_status.
  5. Response – 201 with assignmentId on success; 4xx/5xx on error.

1.7 Important Notes – Assignment

  • Link order ↔ assignment: To show "expert_assigned" when client calls get_detailed_status with orderId only, either assign_itr must write to itr_order_status with the same order_id the client uses, or get_detailed_status must resolve itrId from itr_assignments when only orderId is sent.
  • itr_assignments = source of truth for "who is assigned"; itr_order_status = source of truth for "which step is completed".

Part 2: Status Update Process

2.1 Overview

Purpose: Track and display a 5-step workflow: Payment Success → Expert Assigned → Documents Verified → Filing ITR → Acknowledgement Generated. Steps can be set automatically (payment, assignment) or by professionals (documents_verified, filing_itr, acknowledgement_generated).

Outcome: Client and admin see current step, progress %, and which steps are completed.

2.2 The 5 Status Steps (Order)

OrderStep codeTitleWho sets it
1payment_successPayment SuccessAutomatic (verify_payment)
2expert_assignedTax Expert AssignedAutomatic (assign_itr) or fallback from itr_assignments
3documents_verifiedDocuments VerificationProfessional (update_status_step)
4filing_itrFiling ITRProfessional (update_status_step)
5acknowledgement_generatedAcknowledgement GeneratedProfessional (update_status_step)

2.3 APIs Involved

2.4 Database Tables

itr_order_status – Core table: order_id, itr_id, user_id, status_step, is_completed, completed_at, notes, has_concern.

itr_order_concerns – status_id, order_id, itr_id, user_id, concern_type, concern_text, status.

payment_info – Used for payment display and payment_success fallback.

itr_assignments – Used for expert_assigned display and fallback.

itr_detail, personal_details, document_details, users – For itrDetails and assignment professional name.

2.5 Step-by-Step Status Read Flow (get_detailed_status)

  1. Client calls GET /itr_status/get_detailed_status.php?orderId=... or ?itrId=24 with Bearer token.
  2. Token validated; userId from token.
  3. Load steps from itr_order_status (StatusHelper::getStatusSteps).
  4. Build 5 steps from DB; attach concerns from itr_order_concerns.
  5. Load payment_info; if payment success and payment_success step not in DB, fallback: mark payment_success completed.
  6. If itrId set: load itr_assignments + users; if expert_assigned not in DB but assignment exists, fallback: mark expert_assigned completed.
  7. If itrId set: load itrDetails (itr_detail + personal_details + document count).
  8. Recompute overallStatus, currentStep, progressPercentage.
  9. Return JSON: orderId, itrId, itrStatus (steps, overallStatus, currentStep, progressPercentage), paymentStatus, assignmentStatus, itrDetails.

2.6 Step-by-Step Status Write Flows

Payment success: App calls POST verify_payment → updates payment_info → StatusHelper::updateStatusStep('payment_success', true) → itr_order_status.

Expert assigned: POST assign_itr → INSERT itr_assignments → get order_id from payment_info → StatusHelper::updateStatusStep('expert_assigned', true) → itr_order_status.

Other steps: Professional calls PUT update_status_step with orderId/itrId, statusStep, isCompleted → StatusHelper::updateStatusStep → itr_order_status.

2.10 Important Notes – Status

  • orderId vs itrId: With orderId only, itrId may be null so assignment and itrDetails are not loaded unless backend resolves itrId. Using ?itrId=24 ensures assignment and itrDetails are returned.
  • Fallbacks: get_detailed_status can show payment_success and expert_assigned from payment_info and itr_assignments even when itr_order_status has no row.
  • Query param for ITR id is itrId (camelCase), not itrid.

Summary: Next Move Checklist

  • Assignment journey: Ensure assign_itr writes expert_assigned to itr_order_status with the same order_id the client uses, or ensure get_detailed_status can resolve itrId from assignments when only orderId is sent.
  • Status journey: For orderId-only calls: either resolve itrId from itr_assignments and load assignment + fallback, or ensure assign_itr and verify_payment always write to itr_order_status.
  • Client app: Prefer calling get_detailed_status with itrId when available so assignment and itrDetails are always returned.
